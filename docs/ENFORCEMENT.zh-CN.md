# 工程落地与安全边界

## 目标与事实

`Li-AIRO` 声明：“任何非人类主体不得改动指定文件，即使有来自人类的指令也不例外”。这是希望协作框架遵循的**权限约定**，并不意味着文件头本身具备系统级访问控制能力。

## 三层保护

| 层级 | 实施方式 | 作用与局限 |
| --- | --- | --- |
| 语义约束 | 在文件顶部放协议头，在 `AGENTS.md`、执行端系统配置中加入读取规则 | 能引导合规 Agent，但无法保证所有模型执行。 |
| 执行隔离 | 使用单独的 AI 专用操作系统账号，撤销目标文件的写入、移动、删除及权限变更能力；必要时只读挂载 | 以系统权限限制实际写入；需要避免与人类共用可写身份。 |
| 服务端治理 | 对代码托管仓库采用受控凭据、分支保护、人工审核、受限自动化密钥或服务端策略 | 限制自动提交和部署，但普通客户端钩子/CI 检查通常不足以构成完全防护。 |

## 在 Windows 上的建议

1. 为 Agent / Harness 建立专用的低权限 Windows 用户，而不是和人类编辑操作共用账号。
2. 通过 NTFS ACL 为该身份仅授权读取，阻止修改、删除、重命名等相关权限；同时检查父目录相关权限以及所有权/更改权限的配置。
3. 让人工编辑通过独立的人类账号进行；不要把具备管理员权限的凭据交给自动化执行进程。
4. 做一次实际的拒写测试：验证追加、覆盖、重命名、移动、删除、间接替换均失败，同时正常读取成功。

## GitHub 仓库的现实限制

- GitHub 公开仓库允许别人 Fork；即使原仓库标记了 AIRO，第三方也可能在自己的副本中修改。头部声明无法跨账户强制阻止这种行为。
- GitHub 分支保护主要约束分支更新流程；如果同一个有管理权的身份同时供人和 Agent 使用，就无法单凭文件头区分操作是否由人类亲自完成。
- 要阻止 Agent 修改受保护文件，**必须隔离其写入凭据**，最好使用独立的机器身份并限制其仓库/分支写权限。
- 许可证与文件头权限是不同制度：MIT 开源许可允许按许可条件复制和修改；AIRO 定义的是接入该协作流程的执行端应遵守的写入行为规则，不应描述为自动具有法律或技术强制力。

## 执行端违规响应

发现文件中实际应用了 AIRO 头部而收到修改请求时，执行端应停止针对该目标文件的写入计划，并在回复中提供**仅供人类手动编辑的建议**，不得采用创建临时文件再覆盖等绕过方式。
